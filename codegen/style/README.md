# Material design in codegen_style

`codegen_style` can generate two designs into one binary: the classic one
from the `.style` files and icons as they are, and a Material one from
sibling override files and `icons_material/` icon variants. The generated
`init_<module>()` picks the values with `style::IsMaterial()`
(`ui/style/style_core_design.h` in lib_ui), so the design has to be chosen
before `style::StartManager()` and stays the same until the app restarts.

Every module is parsed twice: as it is, and with the Material overrides of
every module it reads and the Material icon variants applied. Only the
variables whose generated value differs get a Material branch. A module
where nothing differs is generated byte for byte as before.

## Override files

A module `path/X.style` may have a sibling `path/X.material.style`:

```
// Material values of buttons.style.
using "ui/extra_colors.style";

buttonRadius: 10px;
buttonDuration: 150;
defaultButton.padding: margins(12px, 6px, 12px, 6px);
defaultButton.ripple.color: extraRippleColor;
arrowIcon: icon {{ "arrow_down", windowBgActive }};
bigButton: Button(defaultButton) {
	height: 48px;
}
```

- `using "...";` lines work as in a module. They are needed only for names
  that `X.style` itself can't see; such modules are included by the
  Material parse of `X.style`.
- An entry is `name: value;` or `name.field.subfield: value;`. The value is
  any `.style` value: pixels, ints, doubles, bools, strings, colors,
  points, sizes, margins, aligns, fonts, icons, copies and struct values.
  As in a module, a struct value `Type(parent) { ... }` has no `;` after it.
- The value is read at the place where `name` is defined in `X.style`, as if
  it had been written there. It may refer to everything that place can see,
  and everything after it sees the Material value: copies (`a: name;`),
  struct parents (`Type(name)`), field reads (`name.left`) and arithmetic,
  in `X.style` and in every module that uses it.
- A field entry changes only that field. If `name` is a copy of another
  struct, it becomes a struct whose other fields still refer to the fields
  of the original one (`st::original.field`).
- The palette (`.palette` files) has no overrides, colors come from themes.

Errors, all fatal:

| Code | Meaning |
|---|---|
| 802 | the value has another type than the variable or field |
| 803 | no such field, or the path goes through something that is not a struct |
| 810 | the key is not a variable of `X.style` (variables of included modules go to their own override file) |
| 811 | the same key twice, or a key inside another key (`a` and `a.b`) |
| 204 | something follows the value, for example `;` after a struct value |
| 812 | a Material icon variant is incomplete |
| 813 | an override file is used as a module |
| 822 | follows any error of the Material parse |

Limits:

- A whole struct value can't refer to the variable it replaces. Override
  its fields instead.
- Parts of margins, points and sizes (`padding.top`) can't be overridden
  alone. Override the whole value.
- The rule against inheriting an unnamed icon from another module (807)
  applies to Material values too: if a struct field gets a new unnamed icon
  and another module inherits that struct, override a named icon variable
  instead of the field.

## Icon variants

An icon that a module refers to as `"<rel>"` and that is found as
`<root>/icons/<rel>` through the include paths has a Material variant when
`<root>/icons_material/<rel>` exists, under the same include root: either
`<rel>.svg`, or all three of `<rel>.png`, `<rel>@2x.png` and `<rel>@3x.png`.
A partial PNG set is error 812. The variant is read with the same
modifiers (`-flip_horizontal`, `-24x24`, ...), so SVG variants can't take
the flip and rotate modifiers, as with any SVG icon.

The classic and the Material masks are both embedded, and the icon value
takes one or the other. To remove a layer of a multi-layer icon in
Material, give it a variant of the same size that is all black: masks are
converted to RGB32, so a transparent PNG with white color under zero alpha
would become a filled square.

## Generated code

For a module with Material values:

- the source includes `ui/style/style_core_design.h`;
- runs of consecutive variables with Material values are assigned in one
  `if (style::IsMaterial()) { ... } else { ... }`, keeping the order of
  all assignments; the `else` branch has exactly the classic values;
- an `int` or `double` variable is a `constexpr` in the header, unless its
  Material value differs: then it is `extern const int &name;` like the
  other types, starts with the classic value and gets the Material one in
  `init_<module>()`. Code that uses such a value in a constant expression
  stops compiling, which shows where it needs a runtime value;
- classic icon masks keep their indices, Material masks come after them.

The idea of embedding a second mask per icon comes from freshGram's
codegen patch (GPLv3), which picks between them in lib_ui. Here the choice
is made in the generated code and the values come from override files
instead of a table in the generator.

## Build dependencies

The style generation rule lists the `.style` files, but `codegen_style`
also reads the override files and the Material icons. Glob them so that
editing or adding one regenerates the styles, for example in
`generate_styles()` of `lib_ui/cmake/generate_styles.cmake`:

```cmake
    file(GLOB_RECURSE material_dependencies CONFIGURE_DEPENDS
        ${src_loc}/*.material.style
        ${src_loc}/icons_material/*.png
        ${src_loc}/icons_material/*.svg
        ${submodules_loc}/lib_ui/*.material.style
        ${submodules_loc}/lib_ui/icons_material/*.png
        ${submodules_loc}/lib_ui/icons_material/*.svg
        ${submodules_loc}/Resources/icons_material/*.png
        ${submodules_loc}/Resources/icons_material/*.svg
    )
    list(APPEND full_dependencies_list ${material_dependencies})
    list(REMOVE_DUPLICATES full_dependencies_list)
```

## Self-test

`test/` holds a tiny module set and the expected output:

```
python3 codegen/style/test/run_test.py path/to/codegen_style
python3 codegen/style/test/run_test.py path/to/codegen_style --upstream path/to/upstream/codegen_style
python3 codegen/style/test/run_test.py --compare upstream/gen/styles material/gen/styles
```

The first form compares the generated files with `test/expected/` and
checks that every case in `test/errors/` fails with its error code.
`--upstream` also checks the classic output against a `codegen_style`
built from the upstream sources. `--compare` does the same check for two
folders of generated styles, for example of a whole app built once with
each generator: modules without Material values must be identical, the
others must assign the upstream values in their classic branch.
